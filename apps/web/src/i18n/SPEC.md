## Responsibility

Turns the interface copy a component renders into a value a locale can override, without a build-time
extraction step and without a hook.

The English source string **is** the message key. `t("Send")` returns `"发送"` under `zh-CN` and `"Send"`
under `en`, so a component keeps its copy inline and readable, an untranslated key degrades to its English
source instead of an error, and no second file has to be kept in sync with the call sites. Templates use
positional `{0}` placeholders rather than named ones, because Chinese routinely reorders the count or the
object relative to English.

## Boundary

- **Owns:** the `t` lookup and its placeholder interpolation, the `Catalog` type, locale resolution
  (persisted preference → `navigator.language` → `DEFAULT_LOCALE`), the locale set and its picker labels, and
  the bundled catalogs under `catalogs/`.
- **Public surface:** `index.ts` — `t`, `translate`, `formatMessage`, `translateHostMessage`, `getLocale`,
  `setLocale`, `applyLocale`, `resetLocaleCache`, `normalizeLocale`, `storedLocale`, `LOCALES`,
  `DEFAULT_LOCALE`, `LOCALE_LABELS`, and the `Locale`/`Catalog`/`MessageArgs` types.
- **Allowed deps:** `clientPreferences` (the optional native stable adapter) and `@/constants` (the storage
  key prefix). Nothing else in the app: this module sits below `store`, `transport` and every feature view.
- **Forbidden:** importing `store`, `transport`, `panels`, `chat`, or `shell`; holding React state; reading
  the DOM. `t` is a plain function so a module-level constant, a native menu label and a component can all
  use it, and so call sites need no rules-of-hooks discipline.

`registry.ts` is the data-only barrel: the scripts and the tests import the catalogs and the key list through
it, because they run in environments with no `navigator` and no `location`, and importing `index.ts` would
resolve a locale as a side effect.

## Why a reload switches locale

`applyLocale` persists the choice and then reloads. Copy is read by module-level constants, the native
application menu and `document` metadata as well as by components; a re-render would leave those stale, and a
subscription would turn every `t` call site into a hook. One reload is the only change that makes all of them
agree, and it costs nothing in a local app.

The resolved locale also drives `document.documentElement.lang` (`main.tsx`), which is what selects CJK glyphs
and line-breaking rules in the browser and what a screen reader uses to pick a voice. `index.html` keeps a
static `lang="en"` as the pre-boot default.

## Registry and coverage

`keys.ts` is generated by `scripts/i18n-keys.ts` from the `t("…")` call sites, so the registry provably equals
the set of keys the UI can render. `scripts/i18n-coverage.ts` measures each catalog against it and fails below
100% — a locale that is 97% translated is a known quantity, not an invisible one. Keys whose Chinese value is
deliberately the English one (product names, CLI commands, byte sizes) are listed in the catalog's
`IDENTICAL_KEYS`, so "intentionally identical" is never reported as "untranslated".

`scripts/i18n-codemod.ts` and `scripts/i18n-codemod2.ts` performed the initial sweep and stay as the
re-runnable tools for new copy; they are deliberately conservative (they refuse CSS class lists, storage keys,
commands, ANSI escapes and already-Chinese strings) because a wrongly wrapped identifier breaks a build, while a
missed label is only cosmetic. `keys.ts` and `hostMessages.generated.ts` are both generated and therefore
excluded from Biome: formatting them would put the checked-in file and the generator's output out of sync, and
`i18n:check` would report a drift that is only whitespace.

`i18n:check` runs all three generators in verify mode and then the coverage gate, so a hand-written `t("…")`
that nobody translated, a host message added without a translation, and a stale generated file all fail the
build rather than shipping.

## The desktop menu

The native menu and the start-up failure dialogs are shown before the web client loads, so they cannot read a
catalog from it. `apps/desktop/src/menuLocale.ts` holds the same two locales and their menu labels, resolves
the same persisted preference (`thinkrail-locale`) and falls back the same way, including `LC_ALL`/`LANG`;
`menuLabel(locale, key, args)` is its `t`. The preference key and the reload-on-change behaviour are therefore
shared contract, not a coincidence: the web picker writes what the desktop reader reads.

## Host and desktop messages

The host (`packages/server`) formats its failures in English and sends the formatted string as
`Error.message`; it has no locale, no catalog, and its own tests assert that exact text. The desktop process
has the same shape for its updater failures, which it hands to the client as state. Translating in either
place would change a contract the client is not the only reader of, so the translation happens at the display
edge instead — `translateHostMessage`, called from `transport/errorText.ts` for request failures and from the
updates panel for updater state. The wire stays English; the toast does not.

`hostMessages.generated.ts` is generated by `scripts/i18n-host-messages.ts` from the `new Error(…)` and
`new CodedError(code, …)` call sites under `packages/server/src` and `apps/desktop/src`, and from the desktop
updater's own `fail(phase, message)` calls, which reach the client as updater state rather than as thrown
errors. Each message becomes a key (a template
expression's holes become `{0}`, `{1}`, …) plus a `RegExp` that captures what the host interpolated — a path,
a session id, a raw git error — so the sentence around it can be translated with those values slotted back in
in Chinese word order. Longer literals are matched first so a specific message beats a generic one
(`Invalid workspace name: {0}` before `Invalid {0}`). Templates that are pure glue (`${a} ${b}`) are skipped:
their pattern would match almost any text and there is nothing in them to translate.

A message matching no template falls through to a plain catalog lookup, and then to itself — which is what
makes the wrapper safe around client-side errors and untranslated host diagnostics alike.

## Adding a locale

Add the tag to `LOCALES`, add a `LOCALE_LABELS` entry, add a catalog to `CATALOGS`, and extend
`normalizeLocale` if the tag needs aliases (`zh-Hans-CN` and `zh_CN` both normalize to `zh-CN`). The coverage
gate then reports the new locale's gaps from the first run.

## Tests

Component tests run with the locale pinned to `en` (see `apps/web/bunfig.toml` and `src/test-preload.ts`):
the English string is the key, so a behavioural assertion keeps reading the source copy and a translation
change never rewrites a test. Translation completeness is guarded by `i18n:check` in the build instead, and
`apps/desktop/src/menuLocale.test.ts` covers the menu's resolution order.
